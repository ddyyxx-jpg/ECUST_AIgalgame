# 10 · 部署与一致性边界（issue #40）

> **状态**：记录**当前实现**的边界，不是解决方案清单；不表示线上已验证丢数据，也不表示现有单实例试用必须阻断。
> **适用范围**：`origin/main` @ `42690c9`（`CONTRACT_VERSION 3.2.1`）的 FileStore/JSONL 实现。换存储后端后本文必须重写。
> **证据来源**：`packages/engine/src/store.ts`、`packages/engine/src/arbiter.ts`、`apps/server/src/bootstrap.ts` 的源码静态检查；未做多进程竞争写入或线上压测。

---

> **坏档恢复（3.6.1）**：当前加载校验整个文件并实际投影，遇坏档时保留源文件并告警。 磁盘校验遵循已有日志结构，保留合法的长回合引用和引擎生成的复合 ID，并校验私信负载与事件的房间归属一致。其他房间可以启动，坏房间访问返回 `503 E_STORE_FAULT`。停服后保留原档，使用 `npm run replay -- --file <path>` 校验恢复副本；修好或替换后重启即可恢复该房间（重启只重新载入日志、不重放已提交回合），无需额外的重建索引/迁移步骤，其他房间不受影响。

## 1. 一句话结论

当前存档一致性只由**单个 Node.js 进程内**的房间串行链 + 写队列 + 整份「临时文件 → rename」保证：

- **支持单实例**（一个 server 进程独占一个 `data/` 目录）——这是当前唯一被验证的部署形态。
- **禁止多实例 / 多进程 / 多副本共同写同一个 `data/` 目录**，也禁止放在 NFS/SMB 等网络卷上多机共写。
- **备份与升级必须在停写窗口内做**；运行中热拷贝不保证跨文件一致。
- SQLite/WAL、多写者事务、分布式锁均为**规划中**，未实现、未验证、不构成承诺。

## 2. 当前实现（机制与位置）

| 机制 | 位置 | 保证范围 | 跨进程有效？ |
|---|---|---|---|
| 事件日志是真源 | `data/rooms/<roomId>.jsonl`，一行一个 `Envelope` | 单房间追加式事件流，`seq` 连续 | — |
| 整份写盘与同步 | `packages/engine/src/store-write.ts` | 临时文件同步 → 原子替换 → 同步所在目录，确认后更新内存 | 文件原子替换 |
| 写入错误 | `FileStore.writeAll` | 替换前失败可重试。替换后目录同步失败，当前房间暂不可读写，回合结果待核对 | 仅本进程 |
| 进程内写队列 | `packages/engine/src/store.ts:143`、`:256-270` | 同房间的写入在本进程内串行，避免交错 | ❌ 只在进程内 |
| 进程内房间缓存 | `packages/engine/src/store.ts:141-146`（`loaded`/`loading`/`logs`/`states`） | 载入一次后不再读盘；`load()` 之外的读路径都走缓存 | ❌ 看不到别的实例写入 |
| `seq` 校验 | `packages/engine/src/store.ts:258-263`（`E_SEQ_GAP`） | 同一进程内提交的 seq 必须接续 | ❌ 不是跨进程序列分配 |
| Arbiter 每房间串行链 | `packages/engine/src/arbiter.ts:98`、`:110-115`（`chains`/`exclusive`） | 同房间 `apply` 在本进程内排队，避免并发读同一快照 | ❌ 只在进程内 |
| 坏档隔离 | `FileStore.readLog`、`room-log.ts` | 非法事件、序号断档或投影错误会保留原日志并报告存储故障 | — |
| 文件锁 / 租约 / DB | — | 全仓无 `flock`、无锁服务、无 SQLite/DB；`*.db` 仅在 `.gitignore` 里出现 | ❌ 不存在 |

关键点：**单文件 rename 的原子性 ≠ 多个实例之间的事务或互斥。**

---

房间日志与目录只有在系统返回 `ENOENT` 时按缺失处理。权限或 I/O 故障会返回错误并允许下次重读，避免把已有存档初始化为空房间。启动期重建房间索引（`FileStore.listRooms()`）同理：非 `ENOENT` 直接启动失败，不按「没有房间」继续跑。

## 3. 支持的部署形态

| 形态 | 结论 | 说明 |
|---|---|---|
| 单机、单 server 进程 + （可选）nginx 反代/静态托管 | ✅ 支持 | 当前唯一验证形态；反代只做转发，不改变一致性边界 |
| 单机多进程（`node cluster`、`pm2 -i >1`、同一 `data/` 起两个端口） | ⛔ 禁止 | 两个进程各自缓存日志/seq，后写者整份覆盖 |
| 多机 / 多容器 / 多副本共享 volume（NFS/SMB/云盘） | ⛔ 禁止 | 既无跨进程互斥，跨机 rename 的原子性也不保证 |
| 多实例各自独立 `data/` 目录 | ⚠️ 不是高可用 | 只是"多个互不相关的世界"，存档不共享；切勿把 nginx 把同一玩家分到两个后端 |
| 只读副本 / 离线分析 / 备份读取 | ✅ 有条件 | 只能复制**停写窗口**内的快照后读取，不能挂载原目录 |
| 滚动升级 / 蓝绿两套同时写同一卷 | ⛔ 禁止 | 期间会出现两个写者；见 §6 |

## 4. 为什么 `tmp → rename` 不等于多实例事务（issue #40 核心）

1. **原子性范围**：`writeAll` 的原子性只覆盖"用新文件替换这一个 JSONL"（`store.ts:242-249`）。一次提交是「读本进程缓存的日志 → 校验 seq → 写 tmp → rename」的多步本地流程，没有跨进程边界。
2. **seq 在进程内分配**：`append` 用本实例内存里的最后一跳 seq 计算 `expected`（`store.ts:258-263`）。两个实例若都从 seq=11 开始提交，本地校验都能通过，后 rename 者整份覆盖先写者。
3. **没有冲突检测**：`loaded` 置位后 `FileStore` 不再读盘（`store.ts:141-146`、`:168-170`），文件被别的实例改过也不会被发现；没有版本号、mtime 校验或租约。
4. **缓存不失效**：房间状态、`logs`、`seq` 全是进程内缓存；另一实例提交后，本实例 `/state` 仍返回旧投影，直到进程重启。
5. **坏档隔离**：若读到异常日志，保存原件并按房间报告存储故障。已被覆盖的事件可能没有留下断号。
6. **结论**：rename 保证的是"崩溃后文件完整、不会读到半批事件"；它不提供跨进程互斥、事务、冲突检测、读一致性。把当前部署扩为多副本并宣称存档一致性有保障是不成立的。

## 5. 数据备份与恢复（停写窗口）

**原则：先停写，再整体复制 `data/`；恢复同理。**

1. 停止唯一的写实例。当前 `apps/server/src/main.ts` 没有 SIGTERM/SIGINT 优雅停机逻辑，停止后需确认进程已退出、端口已释放。
2. 复制整个 `data/`（保留目录结构）：`rooms/`、`map/`、`users/`、`history/`、`worlds/`、`auth/`、`llm-settings.json`。`auth/` 包含账号库 `auth.json`、额度账本 `ledger.jsonl` 和操作审计 `admin-actions.jsonl`，详见 `docs/02-数据格式.md` §6.4。
3. 启动实例；投影由 `listRooms()` + 事件日志重建（`apps/server/src/bootstrap.ts:278`、`:293`）。

为什么不能热备：单文件原子替换**不等于**跨文件一致。`rooms/`、`map/`、`users/`、`worlds/` 之间没有事务，运行中复制可能拿到不同时间点的文件组合；还可能复制到正在写的 `*.jsonl.tmp`。

恢复：

- 停实例 → 用备份替换整个 `data/` → 启动。
- 备份后校验：`npx tsx scripts/replay.ts --file data/rooms/<roomId>.jsonl`（回放校验投影一致）；`npx tsx scripts/smoke.ts`（新目录跑一回合）。
- `*.jsonl.tmp` 残留：写盘先 tmp 后 rename，崩溃可能留下残余；**确认没有进程在写之后**再删除，运行中不要删。
- `data/` 含账号哈希、凭证摘要、管理审计和模型 key（`llm-settings.json` 权限 0600）。备份需加密、不得进 git。

## 6. 升级 / 发布流程

1. **停写**（同 §5）：确保没有第二个实例在写。
2. **备份** `data/` 并留版本号/commit sha。
3. 部署新代码（契约版本可经 `GET /api/v1/health` 的 `contract` 字段核对）。
4. 启动，检查 health 与启动日志 `galgame engine <version> on ...`。
5. 冒烟：`npx tsx scripts/smoke.ts`。
6. 回滚：停实例 → 回旧代码 + 旧 `data/` 备份。数据格式兼容范围以 `docs/03` §0.4/§0.6 与 `docs/02` §7 为准。

**不要**：滚动升级、蓝绿两套同时写同一卷、升级期间保留旧实例"只读"——当前实现没有只读模式，后台任务也可能写盘。

## 7. 运维检查清单

- [ ] **单写者**：确认只有一个 server 进程/容器写该 `data/` 目录；反代不要分到多个后端。
- [ ] **health**：`curl -s http://127.0.0.1:8787/api/v1/health` 返回 `ok:true` 与预期 `contract`（路由见 `apps/server/src/routes.ts:129`）。
- [ ] **数据目录**：用**绝对路径** `GALGAME_DATA_DIR`（默认 `data` 是相对进程 cwd，换工作目录会读不到旧档）；目录仅服务账号可读写。
- [ ] **密钥文件**：`data/llm-settings.json` 权限 0600，不进 git、不进日志。
- [ ] **磁盘**：每次提交整份重写日志（O(n)，`store.ts:242-249`），留足空间；写失败会以 `E_STORE_FAULT` 暴露，不会静默丢。
- [ ] **日志**：出现 `房间 <room> 暂不可读` 时保留原件，用回放工具核对并按停写流程恢复。
- [ ] **备份**：定期停写全量备份 + `scripts/replay.ts` 校验；做一次恢复演练。
- [ ] **升级**：停写窗口 + 备份 + health/smoke（§6）。
- [ ] **调试模式**：生产环境**不要配置** `GALGAME_DEBUG_PASSPHRASE`。配了就有 `POST /api/v1/debug/unlock` + `GET /api/v1/debug/rooms/:roomId/snapshot`（docs/03 §5.2.12），令牌是**开发者全局视图**——可读任意房间的 NPC 私忆、心理活动、私信，不绑定账号/房间；只给可信开发者、只在本地/内网调试用，切勿暴露给不可信用户或留在共享浏览器（前端关闭面板/登出即清令牌，但服务端令牌 30 分钟内仍有效）。

### 7.1 房间日志的持久性与容量

房间提交成功依赖本地文件系统和底层卷兑现文件与目录的同步语义。服务在加载账号前逐级创建数据根目录并同步父目录，部署提供的已有祖先路径应已持久化。已有路径的父目录仅允许穿越时，可以继续使用预建的数据目录。新建目录仍需成功同步其父目录。若日志已替换但目录同步报错，服务记录原始 I/O 错误，保留磁盘上的日志，暂停该房间读写。冻结标记只在进程内（`FileStore.uncertain`）：重启不会消解可疑结果，重启前必须人工核对磁盘日志。先前已经完成同步的回合仍按自身序号和投影确认，较迟到达的确认不会回退续玩索引。其他房间的后台扫描继续。运维应停服备份并核对磁盘日志及回合结果，随后重新启动。历史、索引和额度账本仍各自写入，房间同步成功并不提供跨文件事务。

在目标磁盘上运行 `TMPDIR=/path/to/scratch node --import tsx scripts/benchmark-store.ts`。脚本在临时目录写入 1 千、1 万和 5 万条合成事件，分别测量加载时间与连续 5 次追加的中位数、最大值。使用与部署卷相同的文件系统，按服务的回合延迟预算确定告警阈值。每次写入仍是 O(日志总字节数)，磁盘应留出完整临时副本的空间。

## 8. 未来演进（规划中，非承诺）

一旦上多实例，必须换成具备跨进程/跨机语义的方案，而不是给 FileStore 打补丁：

- **单写者数据库**：SQLite/WAL 或 Postgres（`docs/02` §6 的 SQL DDL 是设计稿）；仍需把写者收敛为一个进程或由 DB 事务承担互斥。
- **分布式锁/租约**（如 Redis）：跨实例互斥 + 缓存失效/事件总线，否则各实例内存投影仍会陈旧。
- **主从复制 / 只读副本 / 对象存储备份**：读扩展，不替代写者互斥。

在上述任一方案落地并通过多实例竞争写入验证之前，§3 的"禁止"项不变；本文是这些约束的权威出处。

> **跨设备同步（issue #75 项③）本轮不拆子 Issue**：登录/账号已具备，但上述存储后端与互斥方案未落地前，跨设备同步无法独立验收；逐项评估与「拆/不拆」结论见 `docs/02-数据格式.md` §7.1。已拆的可独立验收项为 [#98 多槽存档](https://github.com/ddyyxx-jpg/ECUST_AIgalgame/issues/98)、[#99 导出/导入](https://github.com/ddyyxx-jpg/ECUST_AIgalgame/issues/99)、[#100 历史 200 行上限](https://github.com/ddyyxx-jpg/ECUST_AIgalgame/issues/100)。

## 9. 与本仓库部署资产的边界

- 现状（HEAD `ebff800`）：容器/反代资产**已入库**——`Dockerfile`（Node 22 + tsx 直跑 `apps/server/src/main.ts`，单进程）、`docker-compose.yml`（单个 `app` 服务、`container_name: ecust-galgame`，端口只绑 `127.0.0.1:8787:8787`，`../data:/app/data` 宿主目录绑定挂载，无 `scale`/`replicas`）、`.dockerignore`、`.env.example`、`deploy/README.md`、`deploy/nginx-ecust-galgame.conf`（由 PR #72 新增，`840e9c5` 合入 main）。此前「仓库内没有这些资产、PR #19 未合并」的说法已过期：PR #19 经 PR #71（merge `35e0c57`）回滚后由 PR #72 重提并合入；登录解决"是谁"，不改变"谁能写同一份存档"。
- 这些资产**不改变** §3/§7 的单实例边界：compose 只有一个 server 进程写一份 `data/`，`../data` 是本机目录绑定挂载而非 NFS/SMB/云盘共享卷；不得用 `scale`/多容器/多机共挂同一份 `data/` 扩容，扩容或滚动发布须停旧起新（单写者）。
- `deploy/nginx-ecust-galgame.conf` 无 `upstream` 后端池，只有 `proxy_pass http://127.0.0.1:8787`，即单后端反代 + 静态托管 + IP Host 白名单/443 catch-all 404 与登录/注册限流，**仅用于单副本部署，不用于横向扩展**；切勿把同一玩家分发到两个后端（§3）。反代部署按 `.env.example` 设 `GALGAME_TRUST_PROXY=1`，并让 `GALGAME_PUBLIC_ORIGIN` 与浏览器地址栏的源逐字一致；直连部署保持 `GALGAME_TRUST_PROXY=0`。
- 若将来引入多副本/共享卷/多后端反代，必须先推翻并重写本文 §3/§7 的单实例边界（不是加一行配置就能做），并同步 README 的"限制"。
