**根因**：幂等判定只存在于 `DefaultTurn` 进程内字段；重启后 `seen` 为空，同一个 `clientTurnId`
会被重新结算（再次调 LLM、再次 `apply`）。而权威的事件日志里没有任何「这个 clientTurnId 已提交」的事实，
服务端无法自证。

## 2. 设计

### 2.1 EventLog 持久化回合标记

**核心思路**：把一个「回合已提交」标记事件，与该回合的状态变更事件**放在同一次 `store.append()` 里**。
事件日志是唯一权威（AGENTS I1 / docs/02 §6），因此标记随日志跨重启存活；同批追加保证
「状态已落库但标记没落库」这个裂脑窗口不存在。

**事件名（须先在 docs/03 登记——本次不做）**：

- 推荐**复用已登记的 `turn.committed`**（`docs/03-接口总表.md:564` §4 已有此名，语义「一回合结束」，
  消费方写的是「存档、统计」）。实施前置动作：在 `content/registry/events.json` 补一条
  `{ "type": "turn.committed", "when": "Turn 提交成功后随最后一批事件落库", "broadcast": false }`，
  并在 §4 补 payload 说明。这属于「补缺失条目」，不改已登记语义。
- 备选：新名 `turn.idempotency.marked`。按铁律 #1，**必须先改 `docs/03` §4 登记、再写代码**；
  本次方案阶段只提出候选名，不登记。
- 两者都选 `broadcast: false`：这是服务端记账事实，不是给客户端的领域事件；SSE 给客户端的仍只有
  `turn.commit`（`TurnEvent`）。

**标记 Envelope（建议形状，payload 只增不改，符合 docs/02 §5）**：

```json
{
  "v": 1, "id": "evt_<roomId>_<seq>", "roomId": "<roomId>", "seq": <committedSeq>,
  "ts": <提交时刻>, "actorId": "<actorId>", "type": "turn.committed",
  "causedBy": "evt_<clientTurnId>",
  "payload": {
    "clientTurnId": "<原样>",
    "turnId": "turn_<clientTurnId>",
    "actorId": "<原样>",
    "committedSeq": <与 turn.commit.seq 相同>,
    "replay": [ /* 原样保存的 TurnEvent[]：accepted → [delta] → [facts] → [ui] → patch → commit */ ]
  }
}
```

要点与取舍：

1. **同批原子追加**：`Arbiter.apply` 的 `simulate()` 在生成事件时把标记追加为**最后一条**
   （`packages/engine/src/arbiter.ts:288-301`）。这样标记的 `seq` 就等于本回合 `turn.commit.seq`
   （`turn.ts` 在 flush 后取 `store.seq()`，见 `:344`）。**不选**「提交后再单独 append 一次」：
   两次写之间存在进程崩溃窗口，会留下「已提交无标记 → 重启重复执行」或
   「有标记无状态」的裂脑，恰好是 issue 要修的 bug。
2. **只有成功的那批 apply 带标记**：一回合内 `applyBatch` 最多被调用到第一次成功为止——
   记忆重提（`:216-224`）与修复重提（`:236-275`）都发生在前一批被拒之后，而失败的
   `apply` 根本不 `append`（`arbiter.ts:186-205`）。因此把标记作为内部选项传给每次
   `apply`，只有最终成功的那次会真正落盘，无需「猜哪次是最后一次」。
3. **审核阻断分支要一起覆盖**：`gate.punish` 也会 `apply` 并产出 `turn.commit`（`turn.ts:181-190`、
   `:242-251`，`packages/engine/src/audit.gate.ts:193`），且当前也写 `seen`。若不给它落标记，
   重启后这个已终局的回合会被重放成「重新审核 + 重新处置」。方案要求该分支的 `apply`
   同样携带标记（内部选项经 `punishArgs` 已有 `clientTurnId` 透传）。
4. **标记事件不改世界状态**：`applyEvent` 对未知/新事件走 `default: return state`，所以投影层零影响；
   记忆索引只 `ingest` 原提案事件（`:329`），标记不进记忆。
5. **回放内容为什么整串存**：`TurnEvent` 序列是契约的一部分（`:316-318`，含 `turn.patch` 的
   `state` 快照）。重启后要「返回同一回合」，必须原样重放整串；改用「现算 `snapshot` 拼一个
   patch」拿不到历史时刻的状态，且会破坏事件顺序契约。代价是日志体积增大（叙事文本），
   但叙事文本已在历史投影里落盘（`docs/09` §3），**不引入新的隐私类别**。此为开放问题 Q2。
6. **引擎是闭盒**：上述改动涉及 `turn.ts` / `arbiter.ts` / `audit.gate.ts` 与 `store` 的读法，
   现有扩展点（模块 / 导演 / events.json）不足以在不改引擎的前提下实现「与状态同批落盘的提交事实」。
   按 AGENTS §3 **必须先获得所有者批准才能动引擎**；本方案只陈述必要性，不改引擎。

**重启重建 `seen`**：在 `DefaultTurn.run` 开头 `await store.load(roomId)` 之后
（遵循 `MAJOR-1` 的「先载入再读 seq」，`packages/engine/src/store.ts:8-12`），按房间做一次性扫描：
从 `store.events(roomId, 0)` 过滤 `type === "turn.committed"`，用 zod 在边界解析 payload，
把 `replay` 灌回 `seen`。用 `restoredRooms: Set<RoomId>`（或 per-room 的 restore Promise）防止
重复扫描；扫描放在 `inFlight` 保护区内或与其共用同一把锁，避免「重建中来了并发请求」各自重放。
重建后现有 `seen`/`inFlight` 分支原样生效，不需要新 SSE 事件或新错误码。

### 2.2 `clientTurnId` 键的形状

- **保持现状**：`JSON.stringify([roomId, actorId, clientTurnId])`（`turn.ts:109`）。
  键含 `roomId`/`actorId`，沿用 issue #34 的串台防护；标记 payload 里也显式冗余这三个字段，
  便于人工核查与对账（键本身仍是数组序列化的 JSON 字符串，不改拼写）。
- **与服务端额度键的区别（不要混为一谈）**：§5.2.10 的账本按 `userId + roomId + clientTurnId`
  三元组定位，并校验 `actorId` 一致（`docs/03-接口总表.md:878-884`）。引擎层 `TurnRequest.userId`
  是可选字段（`docs/03:300`），因此引擎幂等键**不加 userId**，维持现有作用域；两层各自独立、
  互不替代。是否统一由所有者拍板（Q3）。
- 历史去重当前按房间内 `actorId + turnId`（`turnId` 已含 `clientTurnId`，`docs/03:800`），
  与本键的 `(roomId, actorId, clientTurnId)` 语义一致。

### 2.3 失败 / 重排队 / 并发 / 重复回放语义

| 场景 | 语义 | 与现状的关系 |
|---|---|---|
| 提交成功（含审核阻断的终局处置） | 最后一批 `apply` 原子落「状态事件 + 标记事件」；`seen.set` 仍在 `flush` 之后 | 新增标记；`turn.commit` 的 `seq` 不变 |
| 失败（`E_SEQ_GAP` / `E_STORE_FAULT` / 提案被拒 / LLM 错误 / 抛错） | **不写标记、不缓存**；客户端可用同一 `clientTurnId` 重排 | 不变 |
| `E_STORE_FAULT` | 写盘先行失败 → 事件与标记都没落库 → 重试安全 | 不变（`arbiter.ts:192-205`） |
| 同 key 进程内并发 | `inFlight` 串行，后来者等首个结算完成再回放同一串 | 不变（`turn.ts:115-126`） |
| 跨重启同 key 并发 | 先按 §2.1 重建 `seen`，再走同一条回放分支；第二个请求不调模型 | 新增能力 |
| 重复请求（进程内） | 命中 `seen` → 原样 yield 整串，含同一个 `turn.commit.seq` | 不变 |
| 重复请求（重启后） | 命中「日志重建的 `seen`」→ 同上；`expectedSeq` 与档案删除检查都被回放分支提前 return 绕过，语义与进程内命中一致 | 新增能力 |
| 新 `clientTurnId` | 正常结算并追加自己的标记 | 不变 |
| 断线后 HTTP 层核对 | 账本 `unconfirmed` 仍可借标记事件做「提交事实」自动对账，替代当前依赖管理员结案的残留风险（`docs/03:876-885`） | 受益，但**账本改造本身属另一任务**，本方案不承诺 |

补充：客户端收到的仍只有 `TurnEvent`（含 `turn.commit`），不新增 `TurnEvent` 分支、不新增错误码；
§7 的 `E_IDEMPOTENT`（`docs/03:979`）现状是「clientTurnId 重复 → 返回已有回合结果」，
引擎侧继续以 200 + 回放流兑现，而不是改 HTTP 状态语义（Q6）。

### 2.4 跨重启重放测试设计

测试文件建议 `packages/engine/src/turn.restart.test.ts`（纯引擎层，不依赖 HTTP），
沿用 `packages/engine/src/store.durability.test.ts` 的 `mkdtemp(tmpdir())` + `FileStore` 模式
（`packages/engine/src/store.ts:140`），每个用例 `afterEach` 清理临时目录。
关键：**重启 = 丢弃全部内存对象，用同一 tmp 目录重建 `FileStore`/`DefaultArbiter`/`DefaultTurn`**。

| # | 用例 | 断言 |
|---|---|---|
| 1 | 提交后日志里存在标记 | 首轮 `run` 收到 `turn.commit` 后，读 `data/rooms/<room>.jsonl`，解析出一条 `turn.committed`，payload 的 `clientTurnId/actorId/committedSeq` 与提交一致；`seq` 与 `turn.commit.seq` 相等 |
| 2 | 进程内重复（回归） | 同一实例第二次 `run` 仍只调 LLM 一次、事件序列逐项相等（对齐现有 `turn.idempotency.test.ts`） |
| 3 | **重启后重复 = 回放** | 新进程的 LLM 端口设计为「一旦被调用就抛错/改返回值」，再 `run` 同一 `clientTurnId`；断言：LLM 未被调用、事件序列与首轮逐项相等、`commitSeq` 相等、`entity.created` 等状态事件不重复 |
| 4 | 不同 key 仍正常结算 | 重启后换新 `clientTurnId` → LLM 被调用一次、新标记落库、新 `turn.commit` |
| 5 | 不同房间 / 不同 actor 同名 key 互不干扰 | 沿用 `turn.idempotency.test.ts:125-138` 的三元组场景，但跨重启执行，验证键形状含 room/actor |
| 6 | 失败不缓存、可重排 | 首轮 using 失败 LLM（如 `E_LLM_FORMAT` 且不可重试）→ `turn.error`，日志无标记；重启后换成功 LLM，同一 `clientTurnId` **正常结算**并落标记 |
| 7 | 写盘失败不产生标记 | 首轮 `store.append` 抛错 → `E_STORE_FAULT`；重启后同一 key 可成功（防「假成功标记」） |
| 8 | 重启后同 key 并发 | 新建 Turn 后同时发两个同 key 请求；断言只回放一次结算，LLM 0 次调用 |
| 9 | 审核阻断回合跨重启 | 首轮审核 `blocked` → 处置分支产出 `turn.commit`；重启后重复同 key 不重跑审核/处置（覆盖 §2.1 要点 3） |
| 10 | 标记是 no-op 投影 | 重启后 `GET` 等价的 `snapshot` 与首轮一致，标记事件不产生额外状态变化（覆盖 §2.1 要点 4） |

补充：若实施时引入 payload 的 zod schema，加一条「坏标记行（半截 JSON / 字段缺失）跳过并告警、
不误判为已提交」的健壮性用例（对齐 `docs/03:885` 对账账本坏行的口径）。

- **会升级为 major 的情况**（本方案刻意避免）：改变幂等键作用域到破坏旧行为（例如改用
  `userId + roomId + clientTurnId` 并使旧请求不再命中）、删除/改已有的 `TurnEvent` 字段、

## 5. 待所有者拍板的开放问题

- **Q1 事件名**：复用已登记的 `turn.committed`，还是新起 `turn.idempotency.marked`？
  （建议复用，少一次命名与索引变更。）

- **Q3 键作用域**：引擎是否要把 `userId` 纳入幂等键以与账本三元组一致？
  （建议不纳入：`userId` 在 `TurnRequest` 是可选字段，改键会破坏现有命中。）
- **Q4 原子性机制**：同批追加（需改引擎，无崩溃窗口）vs 提交后单独 append（引擎改动小但存在裂脑窗口）。
  （强烈建议同批。）
- **Q5 版本**：`3.6.0` 不 bump，还是 minor `3.7.0`？依据 §3，两种解释均可，需明确一种。
