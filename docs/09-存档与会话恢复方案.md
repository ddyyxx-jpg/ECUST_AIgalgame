# 09 · 存档与会话恢复方案（issue #7 MVP）

> 状态：已实现（`feat/save-session`，基于 `CONTRACT_VERSION 3.1.0`）。
> 本文只描述**投影层**（回合历史 + 存档索引）的约定；权威状态仍是房间事件日志，见 `docs/02-数据格式.md` §4 与 `docs/03-接口总表.md` §2.3/§2.9。
> 本方案不新增 op 原语、不改引擎，也不 bump `CONTRACT_VERSION`。

## 1. 目标与非目标

目标（MVP）：

1. 关掉浏览器 / 服务重启后，能从标题页回到上次的房间，看到**之前的对话**，且世界状态与事件日志一致。
2. 标题页有「我的存档」：列出本账号玩过的房间、最后提交到哪，可继续或只删索引。
3. 任何"恢复"都不重播序章、不重新推演、不产生新回合。

非目标（后续里程碑）：跨设备账号体系、云同步、分支存档/读档回溯、多存档位。

## 2. 权威与投影

| 数据 | 位置 | 地位 | 丢了会怎样 |
|---|---|---|---|
| 事件日志 | `data/rooms/<roomId>.jsonl` | **唯一权威状态**（Arbiter 落库） | 房间不可恢复 |
| 回合历史 | `data/history/<roomId>.jsonl` | 投影：已提交回合的对话重放 | 仍可恢复世界状态，只是对话不重放 |
| 存档索引 | `data/users/<userId>/saves.json` | 投影：账号 → 房间列表与游标 | 「我的存档」列表丢，房间还在 |

因此：历史与索引写失败**只告警、不回滚已提交的回合**；恢复时以 `GET /state` 为准，历史只负责把对话铺回屏幕。二者都不允许反向修改事件日志。

## 3. 回合历史

- 路径：`data/history/<roomId>.jsonl`（JSONL，一行一个已提交回合，追加写）。独立目录：`data/rooms/` 只放事件日志，否则 `FileStore.listRooms()` 会把 `*.history.jsonl` 切成幻影房间 id，且未来 append 可能覆盖历史。
- 写入时机：`Turn.run` 外层包装，只在收到 `turn.commit` 后写；`turn.error` / `turn.rejected` / 回滚的回合**不写**。消费者提前断开也不丢（记账在生成器的 `finally` 里执行）。
- 挂载层级：包在 `Turn` 外层而不是 HTTP 路由里，因此 `POST /turns` 与 `map.travel` 等内部回合走同一条记账路径。
- 行格式（`formatVersion: 1`）：

```json
{
  "formatVersion": 1,
  "roomId": "room_xxx",
  "turnId": "clientTurnId 或引擎生成 id",
  "committedSeq": 42,
  "actorId": "plr_1a2b3c4d",
  "userId": "u_xxx",
  "input": "玩家输入原文",
  "narrative": "本回合整段叙事",
  "speakers": [],
  "facts": ["模块给出的人话提示"],
  "createdAt": 1760000000000
}
```

- `narrative` 由 `turn.delta(field="narrative")` 拼接；3.1.0 的事件流没有逐句 speaker，故 `speakers` 固定为 `[]`（预留）。
- 幂等：同一 `turnId` 只记一行（`seen` 缓存重放会再次产出 `turn.commit`）。
- 健壮性：坏行（进程中断留下的半截 JSON）读取时跳过；恢复按 `committedSeq` 升序。缺少历史文件视为空历史，其它读取故障返回 503 `E_STORE_FAULT`。
- 隐私：不含 API key、系统提示词、LLM 原始请求；只含玩家输入、已提交叙事与 facts。
- `userId` 只落盘用于归属/审计，`GET .../history` **不下发**（合作房间里不向他人暴露账号 id）。

## 4. 存档索引

- 路径：`data/users/<safeUserId>/saves.json`（与 `FileImpressions` 相同的目录命名：可读前缀 + `sha256` 前缀，防目录穿越与撞名）。
- 条目（`formatVersion: 1`）：`roomId`、`scenarioId`、`createdAt`、`updatedAt`、`lastTurnId`、`lastCommittedSeq`、`actorId?`。
- `actorId` 是建房时服务端签发的房间内角色 id（`plr_<8hex>`）；新存档必写，3.3 之前的老存档缺省，恢复时从前端传入的存档值 → 房间成员表 → 旧房间兼容值依次兜底。
- 登记：`POST /api/v1/rooms` 在建房成功后按请求的 `scenarioId` 登记；`lastCommittedSeq` 取建房种子事件后的 seq。
- 更新：每次 `turn.commit` 后用同一 `roomId` 推进 `lastTurnId` / `lastCommittedSeq` / `updatedAt`；三者只在序号**前进**时刷新（索引里没有该房间则跳过——建房时没带账号的老房间仍可玩，只是不出现在列表）。
- 删除：`DELETE /api/v1/me/saves/:roomId` **只删索引**，不删房间、不删历史；索引在同一账号内按 `roomId` 幂等，最多 100 条（超出淘汰最久未更新）。
- 写入：先写 `*.tmp-*` 再 `rename` 原子替换；同一 userId 串行。

索引保留最近一次已知的回合进度，迟到的较低或**相同**序号都不会覆盖游标和回合 ID（相同序号是同一回合的重放，`updatedAt` 也不刷新）。缺失时按空索引处理。读取或校验失败时，列表及删除接口返回 `503 E_STORE_FAULT`，回合历史仍按自身的写入结果保留。所有索引写操作保留故障文件供离线修复，合法 v1 文件无需迁移。

### 4.1 索引损坏的处置

索引只是投影：坏了不影响房间与历史，处置时**不要动 `data/rooms/`**。

1. 先确认房间本体正常：`GET /api/v1/rooms/<roomId>/state` 能读到，就说明只是索引坏。
2. 停服并备份故障文件：`mv data/users/<safeUserId>/saves.json{,.bak}`（目录名是「userId 可读前缀-`sha256` 前 24 位」，按 userId 对不上时在 `data/users/` 里 grep 房间 id）。
3. 优先手工修复：把 `.bak` 按 §4 的 `formatVersion: 1` 结构改回合法 JSON（`version` / `userId` / `saves[]` 必填，多余字段会原样保留），放回原路径后重启；`userId` 必须与文件所在账号一致，否则读取按归属不符报 `E_STORE_FAULT`。
4. 实在修不好也可以删掉索引：房间与历史不受影响，「我的存档」少一条、玩家仍可凭本地记录的房间 id 继续。但**索引不会自动重建**——旧房间的条目只能按 §4 手工补回，只有新建房间才会重新登记。删前先留 `.bak`。

## 5. 恢复流程（Web）

1. 本地身份：首次打开生成 `ecust.playerId`（UUID）存 localStorage，之后作为 `X-User-Id`。**开发期方案**：可伪造、可清空，服务端只当"账号名"，不是认证。
2. 标题页挂载时拉 `GET /api/v1/me/saves`，渲染「我的存档」。
3. 进入房间（新建 / 继续上次 / 点存档）：
   - 角色 id：新建用 `POST /rooms` 返回的 `actorId`；恢复用存档里的 `actorId`，缺失时从 `state.room.members` 的 player 成员解析，最后才回退旧值；
   - `GET /rooms/:roomId/state` 取权威状态（失败即按不可用处理）；
   - `GET /rooms/:roomId/history?limit=200` 取历史；
   - 有历史：直接铺「继续上次 · 场景 · 角色 · 已恢复 N 个回合」+ 每行 `input` / `narrative` / `facts`，**不重播序章、不发任何 turn、不走打字机**；
   - 无历史（功能上线前的房间/历史丢失）：退回序章，并提示"世界状态已恢复，对话历史从这次继续开始记录"。
4. 「继续上次」失败时：只有 404（房间真没了；前端映射为 `GameError("E_ROOM_NOT_FOUND")`，该字面量沿用自既有 `/state` 行为、未纳入 `ERROR_CODES`）才清 `ROOM_KEY`；网络错误保留记录并提示重试，避免让人误以为存档被删。
5. 回合提交后刷新存档列表（时间戳/游标更新）；删除存档只刷新列表。

## 6. HTTP 端点

见 `docs/03-接口总表.md` §5.2.7。要点：

- `GET /api/v1/rooms/:roomId/history?fromTurn=&limit=`：本房成员可读；`fromTurn` 支持 turnId 或 committedSeq 数字游标；`limit` 默认 50、上限 200；世界层房间 / 房间不存在 → 404（沿用既有路由层房间不存在响应，不新增错误码），非成员 403 `E_FORBIDDEN`。加载更早历史时，把上一页返回的 `earlierCursor` 原样作为 `before`，可翻过同一 `committedSeq` 的页边界。断流核对确认提交后，同时传入 `turnId` 和 `actorId` 精确读取该回合。
- `GET /api/v1/me/saves`、`DELETE /api/v1/me/saves/:roomId`：账号口径与 `/me` 一致（`X-User-Id` → body → `GALGAME_DEV_USER`）；未带账号时 400 `E_SCHEMA_INVALID`。
- 这些端点只读投影或删索引，不写世界状态，因此不触发 Arbiter，也不改 `CONTRACT_VERSION`。

## 7. 已知限制（MVP 明确接受）

- **身份可伪造**：本地 UUID 不是登录态；换浏览器/清 localStorage 会得到新账号，旧索引看不到（房间本身仍可用 roomId 进入）。
- **历史是投影**：可能因写失败/手工删文件而缺失；缺失时不影响世界状态，只是对话不重放。
- **不重放序章**：恢复时用"继续上次"提示替代序章；老房间没有历史时仍显示序章。
- **speakers 为空**：3.1.0 事件流没有逐句说话人，恢复的叙事是整段文本。
- **只留 100 条索引**：纯列表上限，房间不删。
- **map.travel 也记历史**：内部回合同样经 `Turn`，恢复时会看到旅行产生的叙事；这是刻意选择（否则恢复后的对话会缺段）。
- **历史读取一次最多 200 行**：MVP 一次拉满；更长的房间后续加游标翻页。
- **3.1 之前建房的老房间**：成员表没有 `userId`，知道 `roomId` 者可只读历史（与 `/state` 的开放程度一致，MVP 接受）。

## 9. 后台任务投影与租约（PR-2）

- **为什么**：canonize 定时补扫 / gossip 波次是没有 HTTP 回调驱动的后台工作；进程重启会丢掉"正在跑"的事实，同一任务可能重复执行或永远悬空。追加式 job 投影只记录生命周期（prepared/inflight/done/failed），不写世界状态，因此不触发 Arbiter、也不是存档真相源。
- **存哪**：`data/jobs/<roomId>.jsonl`（`GALGAME_DATA_DIR/jobs/`）。每行一条 `JobRecord`，同一 id 最后一条即当前投影；读文件时坏行跳过并 warn。非真相源，可以直接删：删了只是丢历史，世界状态与回放不受影响。
- **状态机**：`prepared → inflight（attempts+1）→ done（receipt）| failed（lastError）`；`done`/`failed` 是终态，`JobLedger.transition` 拒绝改写终态——重复收尾不会追加第二条 failed（旧 `abortAll` 与 `run` 各写一次 failed 的问题即由这一条 + abortAll 不再写投影共同消除）。投影写入失败只 warn、不阻断任务；**终态写失败**另打固定日志关键字 `[bg] terminal persist failed` 并计入 `BackgroundCycle.telemetry.terminalPersistFailures`（`App.backgroundTelemetry` 可读，进程内累计、不重试），同一条投影不会出现第二条终态。
- **重启 reconcile**：启动时遍历 `store.listRooms()` 逐房对账：`inflight` → orphaned → 标记为 `failed`（`lastError="进程重启时仍在 inflight，按失败处理"`，跨重启只写一次）；`prepared` → runnable，只计数留在 backlog，**本轮不自动重放**（人工/后续 backlog 决策）。对账结果挂在 `App.jobReconcile`（rooms/orphaned/failed/runnable）供运维与测试断言；端到端证据见 `apps/server/src/bootstrap.reconcile.test.ts`。
- **单飞 + 看门狗**：`BackgroundCycle` 每房间同时只允许一个后台任务，忙时直接返回 `{ok:false, reason:"busy"}`（不排队）；超过 `stallMs`（默认取 `GALGAME_BG_STALL_MS`，下限 1s、默认 120s）触发 abort + `{reason:"stalled"}` + failed。
- **运行期遥测（PR #125 复审）**：`App.backgroundTelemetry` 暴露 `terminalPersistFailures` / `watchdogFires`（进程内累计，getter 实时读，不是启动快照）；终态写失败另有固定日志关键字 `[bg] terminal persist failed`。相关单测用轮询（`watchdogFires`、`isBusy`、`/health`）等待条件，不用固定 sleep 当断言，避免 CI 高负载 flaky。
- **锁边界（PR #125 P1-1）**：stall/abort 只结束本次 `run()` 的结果，**不释放单飞锁**；锁保留到任务体真正 settle 才释放（任务体 `canonize.retireRoom` / `gossip.step` 只收 roomId、不接 signal，abort 之后仍会继续跑）。因此超时后同房再 `run` 返回 `busy`，旧任务结束后的下一拍才能进。`waitForIdle(roomId, timeoutMs)` 同样等任务体真正结束（超时返回 false）。
- **卡死边界（PR #125 复审 P2）**：任务体 `canonize.retireRoom` / `gossip.step` 的签名只收 roomId、**不接收 `AbortSignal`**，`abort()` 不会终止它们。若任务体永久卡死（例如 LLM 请求永不返回），该房间会一直 `busy`（同房后续 `run()` 返回 `{ok:false, reason:"busy"}`）、`waitForIdle()` 返回 false，当前**没有强制接管/回收 API**；唯一恢复手段是重启进程（启动 reconcile 把遗留 `inflight` 标 `failed`，单飞锁随进程消失）。后续把「任务体接 signal + 超时强制接管」单独立项跟踪：[#140](https://github.com/ddyyxx-jpg/ECUST_AIgalgame/issues/140)。
- **关停**：`abortAll()` 只 abort 在途 run，终态由各 run 的 abort 分支写一次（`lastError="aborted: shutdown 中止在途任务"`），返回时终态已落盘但不等待任务体 settle。`apps/server/src/main.ts` 用 `shutdownBackground(background, close)` 接 SIGTERM/SIGINT：先中止后台任务、再关 HTTP。**终态落盘证据（复审）**：`apps/server/src/bootstrap.shutdown.test.ts` 用真实 `createApp` + 慢任务 + `shutdownBackground`，在 close 回调里读 `data/jobs/<roomId>.jsonl`，断言在途 job 恰一条 `failed` 且 `lastError` 含 shutdown；真进程 smoke（`main.shutdown.test.ts`）只保留轮询 health/SIGTERM 断言——真进程的后台任务只由定时器触发，无法确定性制造"在途 job"，故拆成装配层端到端 + 进程层 smoke 两层。**已知边界**：若终态投影写入本身永久 hang（极端 I/O 挂起），`abortAll()` 会一直等 `runFinished` 而被拖住，当前没有强制放弃超时，靠进程退出兜底。
- **时钟**：`JobLedger` 支持注入 `now`，`bootstrap` 与 `BackgroundCycle` 用同一时钟，避免投影 `updatedAt` 与调度器时间线不一致。
- **边界**：不改契约（`CONTRACT_VERSION` 不 bump；#124 合入后为 3.7.0），不新增 HTTP 端点；`canonize scanMinutes=0` / `GALGAME_GOSSIP_SCAN_MS=0` 时对应定时器不启动，行为与 PR-2 之前一致。
- **长期 backlog**：jobs 投影只增不减、`list()` 每次全量读文件；房间数/任务数上来后需要按大小轮转或 compact（例如把 done 超过 N 条折叠成快照），否则单房文件会无限长、对账启动成本线性上升。
- 新增：`apps/server/src/job-ledger.ts`、`apps/server/src/background-cycle.ts` 及对应单测（含对账端到端测试 `apps/server/src/bootstrap.reconcile.test.ts`、关停端到端测试 `apps/server/src/bootstrap.shutdown.test.ts`、SIGTERM 真实进程 smoke `apps/server/src/main.shutdown.test.ts`）；修改 `apps/server/src/bootstrap.ts`（装配 + reconcile + 两个定时器接入 + 导出 + `backgroundTelemetry`）、`apps/server/src/config.ts`（`backgroundStallMs`）、`apps/server/src/main.ts`（SIGTERM/SIGINT 关停钩子）。

## 10. 客户端前台恢复（PR-3）

- **为什么**：合盖/切后台/断网再回来时 SSE 可能已经断了，画面停在旧状态；服务端当前没有 `plot.ping` 的发射点，前端无法靠心跳判断流是否还活着，只能信「回到前台 / 网络恢复」这类本地信号。
- **触发条件**（全部满足才重拉）：
  - `document.visibilityState === "visible"` 且 `navigator.onLine`；
  - 局内（`screen === "game"`）且有当前房间；
  - 没有回合在途（`busy === false`，避免和正在收的 SSE 抢状态）；
  - **离开 ≥5s**（`DEFAULT_MIN_AWAY_MS = 5000`）：只约束 visibilitychange / focus 这类前台触发，低于 5s 视为 alt-tab 抖动；网络恢复（`online`）不受此限。
  - **距上次同步 ≥30s**（`DEFAULT_MIN_INTERVAL_MS = 30000`）：所有触发共用；失败同样计一次同步。
  - 输入框里有草稿不再阻止恢复：重进房会在 reset 前捕获、成功后恢复草稿（见下）。
- **动作**：重走一次 `enterRoom(roomId, { resumed: true })`，全量重拉权威状态 + 历史 + 事件回放；发起成功后刷新「上次同步」时刻。**正常进房（首次/换房）成功后也会回写「上次同步」时刻**（`SessionResync.markSynced()`），否则 `lastSyncAt` 停在 0，刚进房就切后台 6s 回来会被判成「很久没同步」而立即全量重拉。决策在 `apps/web/src/session-signal.ts`（纯函数），事件注册/离开时长/节流/防重入/失败提示在 `apps/web/src/session-wiring.ts`（deps 注入，node 环境用 fake 事件源可测完整链路），`App.tsx` 只注入真实 DOM 并注册监听。
- **边界**：
  - SSE 一切正常时也会偶尔多一次全量拉取，属可接受成本；不新增协议、不改服务端、不新增依赖（仍不引 jsdom）。
  - 重进房**先拉数据、成功后才 reset**：拉取失败不清空画面，旧状态、草稿与可重试状态保留，只通过 `eventsNotice` 提示；失败也计一次同步，避免断网时 focus/online 反复重拉（30s 后可重试）。「reset 必须在两次 fetch 之后」由 `apps/web/src/room-enter.ts` 的 `loadRoomThenReset` 保证并被测试钉死（fetchState/fetchHistory 失败或请求作废都不会 reset）。
  - **resumed 重进房期间占位 `busy`**：从发起恢复到 UI 切换完成禁止新回合，避免玩家回合与随后 reset 的旧快照/历史互相覆盖（也避免 `resetRoomUi` 清掉新回合的 busy 状态）；失败或请求作废时解除，成功后由 `resetRoomUi` 归零。只对 `resumed` 生效，普通进房不占位。
  - 同房间重进房保留已探测的 `convMode`（v2 不会在 reset 后、重新探测前误走 v1 回合）与输入草稿；换房/新开局仍按原逻辑清空。
  - 不做前端增量归并：复用 `enterRoom` 一次对齐全部投影，避免复制服务端的事件归并逻辑、出现两套真相。
- **常量**：5s / 30s 的具体用途见 `apps/web/src/session-signal.ts` 的 `DEFAULT_MIN_AWAY_MS` / `DEFAULT_MIN_INTERVAL_MS` 注释；纯前端策略，服务端不感知。
