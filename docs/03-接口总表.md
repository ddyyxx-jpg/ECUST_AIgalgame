## 0. 命名总则

### 0.1 六条规则

| # | 规则 | 反例 |
|---|---|---|
| R1 | **点分命名空间**：`<ns>.<verb>`，全小写，单词用 `_` 连接 | `buyItem` / `Trade.buy` |
| R2 | **名词用单数**，不用复数 | `items.list` ✗ → `item.list` ✓ |
| R3 | **动词用祈使式**，不加时态 | `bought` ✗ → `buy` ✓ |
| R4 | **模块内接口必须带模块 id 前缀**：`<moduleId>.<verb>` | 模块 `trade` 的工具只能叫 `trade.*` |
| R5 | **保留命名空间禁止被模块占用**（见 §0.2） | 模块不能叫 `mod` / `npc`；唯一例外是引擎自带的基础动作模块 `content/modules/core` |
| R6 | 名字一旦随版本发布，**只增不改不删**；废弃用 `deprecated` 标记并保留 ≥2 个版本 | 直接把 `trade.buy` 改名 |

### 0.2 保留命名空间

| 命名空间 | 归属 | 用途 |
|---|---|---|
| `core` | 引擎 | 移动/观察/等待/说话等基础动作（实现放在 `content/modules/core`，属于引擎自带模块，其他模块不得占用该前缀） |
| `world` | 引擎 | 时钟、地点、天气、事件 |
| `actor` | 引擎 | 玩家/NPC 通用能力（任何 actor 都能做） |
| `npc` | 引擎 | 自主行为、对话调度 |
| `mem` | 引擎 | 记忆读写 |
| `plot` | 引擎 | 剧情线/密谋 |
| `mod` | 引擎 | 模块元操作（`mod.load`、`mod.reload`） |
| `net` | 引擎 | 房间、成员、同步 |
| `view` | 引擎 | 视图数据下发 |
| `admin` | 引擎 | 仅本机/内网 |
| `x` | **AI 自由区**（见 §0.5） | AI 推演时临时产生的属性/标记 |

> 模块 id 不得与上表重名（启动时校验，冲突即拒绝启动）。

### 0.3 实体 ID 规范

```
<kind>_<slug>              例：npc_zhangsan, loc_classroom_2_3, item_bread
<kind>_<slug>_<n>          需要区分实例时：mem_1a2b3c, plot_0007
```

| kind | 含义 | 谁创建 |
|---|---|---|
| `plr` | 玩家 | 引擎 |
| `npc` | 非玩家角色 | 内容种子 / AI 推演 |
| `loc` | 地点 | 内容种子 / AI 推演 |
| `item` | 物品 | 内容种子 / AI 推演 |
| `fact` | 客观事实（canon） | 仅人工 |
| `lore` | 软设定（AI 可增删） | 内容种子 / AI 推演 |
| `plot` | 剧情线/事件 | AI |
| `mem` | 记忆条目 | 引擎 |
| `evt` | 事件（日志） | 引擎 |
| `room` | 房间（单人/联机） | 引擎 |
| `mod` | 模块实例 | 引擎 |

- `slug` 只允许 `[a-z0-9_]`，长度 2~32；中文名只存在 `name` 字段里，**不进 id**。
- ID 全局唯一，**永不复用**（删除 = `tombstone`，见 `02-数据格式.md` §6）。

**记忆的保留 ID（3.1.0 起）**：

| 名字 | 类型 | 说明 |
|---|---|---|
| `mem_world` | ownerId | 世界层永久记忆的固定 owner。**它不是实体**，`memory.write` 对它跳过实体存在性校验 |
| `room_world_<worldId>` | roomId | 每个世界一个保留房间，只存 `tier=permanent`，无成员、不可进入 |
| `mem_<contentHash 前 12 位>` | 记忆 id | 有 `contentHash` 时用它（永久层幂等键） |
| `mem_<roomId>_<tick>_<seqInTurn>` | 记忆 id | 无哈希时用它；`seqInTurn` = 本次 apply 内该条提案的序号（同回合同 owner 同 tags 也不撞） |

### 0.4 版本号

| 东西 | 字段 | 语义 |
|---|---|---|
| 接口契约（本文） | `CONTRACT_VERSION` | 语义化版本；破坏性变更 → major |
| 模块 | `manifest.apiVersion` | 整数，引擎只认 `1`（v2 起为 `2`，见下） |
| 数据格式 | `schemaVersion` | 每个 schema 文件内 `$id` 尾段 |
| 事件 | `v` | 事件 payload 形状版本，默认 `1` |

> `apiVersion` 变更策略：**只有当 §3 的 op 原语集合变化时才 bump**。新增模块/工具/属性/事件类型**永不** bump（这就是"只加变量不改引擎"的机制保证）。

### 0.5 `x.` 自由区（AI 推演专用）

AI 在推演中产生的**临时属性/标记**一律放进 `x.` 前缀：

```json
{ "op": "attr.set", "args": { "entityId": "npc_zhangsan", "key": "x.mood_hint", "value": "躲闪" } }
```

- 引擎对 `x.*` **不做类型校验**，按 `number | string | boolean` 原样存。
- `x.*` 只能在**本房间内**可见，不进 canon、不进全局检索、**不得被叙事层当作硬事实引用**。
- 每回合 `x.*` 写入上限 8 条；单实体上限 32 个 key（超出按 LRU 淘汰）。
- 想让某个 `x.*` 转正 → 人工在 `content/registry/attrs.json` 声明正式 key，然后 `attr.set` 迁移。

> 这条是"AI 可以自由增减，但引擎不被污染"的关键闸门。

### 0.6 变更影响矩阵

| 你改了 | 必须做什么 |
|---|---|
| 新增模块 | 加一个目录 + `manifest.json`（启动自动扫描 `content/modules/*/manifest.json`，**无需登记**）。**不动引擎** |
| 新增属性 | `content/registry/attrs.json` 加一条 + UI 字段映射（可选）。**不动引擎** |
| 新增 LLM 工具 | manifest `tools` 加名 + 实现 handler。**不动引擎** |
| 新增事件类型 | `content/registry/events.json` 加一条。**不动引擎** |
| 新增 op 原语 | 本文 §3 + 引擎 `Arbiter` + bump `apiVersion`。**动引擎（尽量避免）** |
| 改 op 语义 | bump `CONTRACT_VERSION` major + 全体模块回归 |
| op 只**新增可选**参数、旧参数旧行为不变 | bump **minor**（例：3.0.0 → 3.1.0 的 `memory.write` 新字段）；旧提案仍合法，不需要改模块 |
| 新增拒绝路径（旧提案可能开始被拒） | minor 但在 §10 变更表写明"新增拒绝"；若会让**已发布内容**失效则按 major |

> 判定顺序：先问"旧提案还能不能原样提交并得到原结果"。能 → minor；不能 → major。
> 3.1.0 属于 minor：`memory.write` 旧 6 字段语义不变，新字段只在显式传入时触发新路径；但新增了两条拒绝路径（世界层 `E_MEMORY_WORLD_MISMATCH`、旧 `visibility:"scene"` 归一为 public），所以 §10.10 不能用"全是只增"来概括。

## 1. 分层与名字归属

```
Client ──HTTP/SSE──> Transport ──Envelope──> Router
                                                │
                                             Turn.run
                                                │
                    ┌───────────────────────────┼───────────────────────┐
                 Modules                      Dialogue                 Memory
              (modules/*)                 (directors/*)            (engine)
                    └──────────────► Arbiter.apply ◄─────────────────┘
                                          │
                                     EventLog / Snapshot
```

- **只有 `Arbiter.apply` 能写世界状态**。模块、导演、记忆、UI 全部产出 `Proposal[]`。
- **只有 `Transport` 接触网络**。引擎不知道 HTTP/WS/SSE 的存在，只知道 `Envelope`。

> 路径：`packages/shared/src/contract/`。这些类型是**冻结契约**，实现可换，签名不可随意改。

### 2.1 基础类型

```ts
/** 统一信封：所有跨子系统消息都用它 */
interface Envelope<T = unknown> {
  v: 1;                      // payload 版本
  id: string;                // 消息 id（evt_xxx）
  roomId: string;
  seq: number;               // 房间内单调递增，用于去重与断线续传
  ts: number;                // 服务器时间戳 ms
  actorId: string;           // 发起者：plr_* / npc_* / sys
  type: string;              // 见 §5
  payload: T;
  causedBy?: string;         // 触发它的上一条消息 id
}

/** 世界状态 = 实体集合 + 房间元信息 */
interface WorldState {
  schemaVersion: number;
  room: RoomState;
  entities: Record<string, Entity>;   // id -> 实体
  links: Link[];                      // 关系/持有/在场等边
  clock: GameClock;
}

interface Entity {
  id: string;
  kind: EntityKind;                   // plr|npc|loc|item|fact|lore|plot
  name: string;
  attrs: Record<string, AttrValue>;   // 键必须在 registry 或 x. 区
  tags: string[];
  origin: "seed" | "ai" | "system";   // 谁创造的

  status: "active" | "dormant" | "tombstoned";

  updatedAt: number;
}

```

### 2.3 裁决器 `Arbiter` —— 唯一写入口

```ts
interface Arbiter {
  /**
   * 校验 + 应用 + 落日志。默认 **atomic：要么全成功，要么全回滚**（02 §4）。
   * 同一房间的 apply 在实现里串行排队，并发提交不会交错读同一份快照。
   */
  apply(roomId: string, ops: Proposal[], cause: Envelope, opts?: ApplyOptions): Promise<ApplyResult>;
  /** 只校验不落库、不消耗回合预算（干跑，给 UI 预览与测试用） */
  dryRun(roomId: string, ops: Proposal[]): Promise<ValidationResult>;
}

interface ApplyOptions {
  mode?: "atomic" | "partial";  // 默认 atomic；partial 是显式选择（坏条目丢弃、余下照做）
  expectedSeq?: number;         // 乐观并发：与当前 seq 不符 → 整批拒绝 E_SEQ_GAP
}

interface Proposal {
  op: string;                       // §3 的 12 个原语之一
  args: Record<string, unknown>;    // 每个原语的参数见 §3
  reason?: string;                  // ≤60 字，写进日志便于排查
  by?: string;                      // 产生者：mod.trade / npc.director / engine.turn
}

interface ApplyResult {
  ok: boolean;                      // "这批到底提交了没有"：atomic 下有拒绝即 false；partial 下只要提交了就 true
  mode: ApplyMode;                  // 实际采用的语义，写进日志便于回放与审计
  seq: number;                      // 落库后的最新 seq
  applied: Proposal[];
  rejected: { proposal: Proposal; code: ErrorCode; detail: string }[];  // 必须能被调用方追溯到来源
  events: Envelope[];               // 本次产生的领域事件（atomic 失败时为空）
}

type ApplyMode = "atomic" | "partial";
```

**提交语义（v2.3.0 起明确）**

| 模式 | 谁来用 | 语义 |
|---|---|---|
| `atomic`（默认） | 玩家回合、交易、密谋落账 | 任何一条被拒 → 整批不落库；`ok=false`，`events=[]`，状态与 seq 不变 |
| `partial` | 显式需要的批处理（如一次写入多条非关键 x. 数据） | 坏条目进 `rejected[]`，余下照做；提交成功则 `ok=true` |

> **拒绝必须被编排层消费**：`Turn` 不允许"有 rejected 还 commit"。模型提案被拒 → 带原因修复最多一次；模块提案被拒 → `E_MODULE_FAULT`；修不好 → `turn.error`，且不产生 `turn.delta`（叙事只能在裁决之后发）。

```ts
// 附：整批失败的形状 —— 没有"哪条 proposal 被拒"可说时用 error，不要伪造占位提案
interface ApplyResult {
  ok: boolean; mode: "atomic" | "partial"; seq: number;
  applied: Proposal[]; rejected: Rejected[]; events: Envelope[];
  /** E_SEQ_GAP：expectedSeq 与当前 seq 不符（重放后重试）；E_STORE_FAULT：落盘失败（状态未变，可直接重试） */
  error?: { code: ErrorCode; message: string };
}

// 附：Store 的落盘契约（内存提交 ≠ 可靠存档）
interface Store {
  snapshot(roomId): Promise<WorldState>;
  events(roomId, fromSeq, limit?): Promise<Envelope[]>;
  replay(roomId, toSeq?): Promise<WorldState>;
  /** 等已追加事件真正落盘；Turn 必须在 turn.commit 之前 await，失败则 E_STORE_FAULT */
  flush(roomId: string): Promise<void>;
}

// 附：引擎内部的 EventLog（**只给 Arbiter/Turn**，模块与前端看不到）
interface EventLog extends Store {
  /** 先载入持久层再返回 seq —— 校验 expectedSeq 前必须用它（重启后懒加载会给 0） */
  load(roomId: string): Promise<number>;
  seq(roomId: string): number;      // 内存视图，未 load 前不可信
  state(roomId: string): WorldState;
  /** 文件实现是 async：**写盘成功后才改内存**，失败则内存与 seq 都不变 */
  append(roomId: string, envs: Envelope[]): void | Promise<void>;
}
```

### 2.4 回合引擎 `Turn`

```ts
interface Turn {
  /** 玩家一次输入 → 一次完整回合（含模块、LLM、裁决、记忆） */
  run(req: TurnRequest): AsyncIterable<TurnEvent>;   // 流式，SSE 直接透传
}

interface TurnRequest {
  roomId: string;
  actorId: string;                  // 谁在行动（联机时可能是 NPC）
  input: string;                    // 自然语言原文
  clientTurnId: string;             // 客户端幂等 id，重复提交返回同一回合
  userId?: string;                  // 3.1.0：账号维度；单人从房间成员取，联机由 route 按登录态注入
  options?: { debug?: boolean; skipLLM?: boolean; budget?: number; expectedSeq?: number };  // expectedSeq 不符 → turn.rejected(E_SEQ_GAP)
}

type TurnEvent =
  | { type: "turn.accepted"; turnId: string }
  | { type: "turn.delta"; field: "narrative" | "dialogue"; text: string }
  | { type: "turn.facts"; facts: string[] }             // 模块给出的既成事实
  | { type: "turn.tool"; name: string; args: unknown; result: unknown }
  | { type: "turn.patch"; ops: Proposal[]; state: WorldState }  // 裁决后的增量
  | { type: "turn.ui"; view: ViewPatch }
  | { type: "turn.commit"; turnId: string; seq: number; usage?: Usage }
  | { type: "turn.rejected"; code: ErrorCode; message: string; retryable: boolean }  // 开工前就被拒（如 expectedSeq 过期），没有 accepted
  | { type: "turn.error"; code: ErrorCode; message: string; retryable: boolean };

// 事件顺序是契约的一部分（客户端可以据此判断"能不能把叙事当真"）：
// accepted → [delta] → [facts] → [ui] → patch → commit
// 裁决失败：accepted → error（没有 delta / patch / commit）
```

> `TurnEvent` 的 `type` 就是 SSE 的 `event:` 字段，一字不改。

### 2.6 记忆 `Memory`

> 3.1.0 起 `Memory` 是**事件日志的索引投影**（`memory.written` / `memory.tombstoned` → `MemoryRecord`），
> 不是独立真相源：服务重启后由 `rebuild(roomId, store.events(roomId, 0))` 重建。
> 正式写路径唯一：`Proposal → Arbiter.apply → 事件 → ingest`；`write()` 只保留给测试。

```ts
type MemoryTier = "short" | "long" | "permanent";
type MemoryStatus = "current" | "historical" | "tombstoned";

interface Memory {
  /** 按打分召回；secret 走强制通道（forced 不占预算） */
  recall(q: MemoryQuery): Promise<MemoryHit[]>;
  /** 纯派生：不创建实体、不产事件；无记录返回 null（空档案 ≡ 无记录，不违反 I1） */
  profile(userId: string, ownerId: string, roomId: string): Promise<MemoryProfile | null>;
  compact(roomId: string, ownerId: string): Promise<{ impressions: number; archived: number }>;
  /** 测试用，不参与正式写路径 */
  write(roomId: string, drafts: MemoryDraft[]): Promise<void>;
}

interface MemoryQuery {
  roomId: string;             // scope="world" 时传 room_world_<worldId>
  userId?: string;            // 给了就按账号过滤（私忆隔离：A 的 private 记忆 B 查不到）
  ownerId: string;            // 谁的视角（决定能看到什么）
  tiers?: MemoryTier[];       // 缺省 = 全部
  scope?: "room" | "world";
  worldId?: string;
  about?: string[];
  tags?: string[];
  budgetTokens: number;
  nowTurn: number;
}

interface MemoryProfile {
  userId: string;
  roomId: string;
  ownerId: string;
  firstMetTurn?: number;
  familiarity: number;        // 0~1 派生
  impressionIds: string[];    // 该 owner 记住的 permanent 条目
  impressions: number;        // 账号级世界印象计数（跨房间）
  lastTopics: string[];
  seenImpressionIds: string[];
}

interface ImpressionNotice {
  id: string;
  memoryId: string;
  userId: string;
  worldId: string;
  subjectText: string;        // ≤40 字，去掉私密细节
  npcId?: string;
  createdAt: number;
  deliveredAt?: number;
}
```

`MemoryRecord` 在 §10.1 的类型补全表里给完整字段（记忆段：`tier`/`status`/`worldId`/`userId`/`sourceRefs`/`contentHash`/`aboutUserIds`）。

**回合里的记忆链路（P1 实现，行为契约）**

1. **读**：`Turn` 先 `store.events(roomId, 0)` 增量喂给 `Memory.sync`（重启后也成立），再按 `ownerId` 召回三层：
   S1.5 世界层永久记忆（`scope:"world"`、`ownerId:"mem_world"`、≤200 tok）→ S7 长期（≤700）→ S8 短期（≤200），
   三段合计硬顶 **1100 tok**；块内按 `memoryId` 排序，保证提示词逐字节稳定（KV 缓存）。
   `ownerId` = 场景里唯一的 NPC；没有明确对谈对象时是玩家自己。
2. **写**：模型输出的 `memory[]` 先过 `LlmMemoryDraftSchema`（无 `ownerId`，`tier` 只允许 `short|long`），
   再过六道闸门（归属/形状/去重/重要度下限/秘密/配额），最后变成 `memory.write` Proposal。
3. **裁决**：记忆提案与模块/模型提案同批 `apply`；若**只有**记忆提案被拒，整批重提一次（去掉记忆），
   回合照常提交并在 `facts` 里加一条「记忆写入被拒」。记忆写坏不许毁掉玩家的合法行动。
4. **落库后**：`applied.events` 逐条 `Memory.ingest` —— 读路径与写路径共用同一份事件日志，回放必然一致。
5. **读失败**（记忆服务异常）：本回合按"第一次见面"继续，`facts` 加「记忆暂不可用」，绝不向玩家抛错。

世界层 `permanent` 只能由 `canonize` 发起、`ownerId` 固定 `mem_world`、房间固定 `room_world_<worldId>`、
必须 `public` + 带 `contentHash` + `sourceRefs`；同 hash 重复写幂等，内容不同 → `E_MEMORY_IMMUTABLE`。

### 2.7 对话导演 `Dialogue` —— NPC 自主多 agent 对话的唯一入口

> **密谋、闲聊、课堂讨论、玩家插入对话，全部是 `DialogueDirector` 的不同实现**。引擎只提供会话骨架（谁在场、谁能知道什么、发言顺序、写谁的记忆），不关心剧情是"密谋"还是"八卦"。

```ts
interface Dialogue {
  /** 开一场会话：参与者 ≥1 个 NPC，可含玩家 */
  open(spec: DialogueSpec): Promise<DialogueSession>;
  /** 推进 1 轮（内部可能调用 0~N 次 LLM） */
  step(sessionId: string): Promise<DialogueStep>;
  /** 玩家插入发言（联机/单人通用） */
  interject(sessionId: string, actorId: string, text: string): Promise<DialogueStep>;
  close(sessionId: string, outcome?: string): Promise<DialogueSummary>;
}

interface DialogueSpec {
  roomId: string;
  participants: string[];          // actorId 列表，≥1
  directorId: string;              // 用哪个导演（见下）
  seed?: Record<string, unknown>;  // 导演自有参数（密谋传 plotId）
  maxTurns?: number;               // 默认 3
  visibility?: "private" | "scene";// private=只有参与者知道
}

interface DialogueStep {
  sessionId: string;
  turns: ChatTurn[];               // { actorId, text, emotion, thought? }
  done: boolean;
  proposals: Proposal[];           // 导演产出的状态变更（守卫值、关系等）
}
```

**内置导演（均可替换/新增，不需要改引擎）**：

| `directorId` | 用途 | 何时触发 |
|---|---|---|
| `npc.plot` | 夜间密谋（v1 §6 的编排器） | 夜晚 tick |
| `npc.smalltalk` | NPC 之间随机闲聊（填充世界） | 空闲 tick，低频 |
| `npc.react` | NPC 对某事件的一致/分歧反应 | 事件触发 |
| `npc.player` | 玩家与 1~3 个 NPC 的多人对话 | 玩家主动发起 |
| `npc.debate` | 课堂/会议式多方讨论 | 模块触发 |

### 2.8 传输层 `Transport`

```ts
interface Transport {
  /** 当前连接的订阅（HTTP-SSE 或 WS，实现可换） */
  subscribe(roomId: string, actorId: string, fromSeq: number): AsyncIterable<Envelope>;
  publish(env: Envelope): void;
  presence(roomId: string): PresenceSnapshot;
}
```

### 2.9 快照与回放 `Store`

```ts
interface Store {
  snapshot(roomId: string): Promise<Snapshot>;         // 全量状态 + seq
  events(roomId: string, fromSeq: number, limit?: number): Promise<Envelope[]>;
  /** 从快照 + 事件重放（测试/断线续传/反作弊共用） */
  replay(roomId: string, toSeq: number): Promise<WorldState>;
  /** v2.3.0 起：等已追加事件真正落盘（内存实现 no-op）；Turn 必须在 commit 前 await */
  flush(roomId: string): Promise<void>;
}
```

> **持久化三条纪律**（Issue #1 复审后固化，`packages/engine/src/store.ts` 实现）：
> 1. **写盘先行**：`append` 成功落盘后才改内存。失败 → 内存/seq 不变 → `ApplyResult.error = E_STORE_FAULT`，`Turn` 不发 commit，客户端重试安全。
> 2. **读前先载入**：`expectedSeq` 校验必须用 `load()` 返回的 seq；直接用懒加载前的 `seq()` 会在重启后首回合假报 `E_SEQ_GAP`。
> 3. **坏档可修**：载入时遇到 seq 断档/重复，保留连续前缀并把修复结果写回，房间仍可进（丢的是断档之后的尾部事件）。

## 3. Op 原语（**闭集，12 个**）

> 这是整个系统的"指令集"。新玩法**只能用这 12 个原语组合**，不得新增（新增 = bump `apiVersion`）。
> 每个原语的具体字段、校验规则、事件产出见 `02-数据格式.md` §4。
> **参数形状的机器可读真源是 `packages/shared/src/contract/types.ts` 里的 `XxxArgs` 与 `packages/shared/src/zod/op.ts`**；本表若与它们不一致，以代码为准并请报告（`npm run check:contract` 会拦 op 名与错误码，不拦参数字段）。

| # | op | 参数 | 说明 | 产出事件 |
|---|---|---|---|---|
| 1 | `attr.delta` | `{entityId, key, delta, mustKeep?}` | 数值增减（clamp 到 min/max 与回合累计额度；`mustKeep:true` 时被钳制即整条拒绝 `E_PRECONDITION`，用于支付/消耗） | `attr.changed` |
| 2 | `attr.set` | `{entityId, key, value}` | 直接赋值（字符串/布尔/枚举） | `attr.changed` |

| 情况 | 结果 |
|---|---|
| `key` 未在 registry 且不以 `x.` 开头 | `E_ATTR_UNKNOWN`，丢弃该条 |

## 5. 协议层（HTTP / SSE / WS）

### 5.1 原则

- 所有响应体统一 `{ ok: boolean, data?, error?: { code, message } }`。
- 所有流式用 `Envelope`，`event:` 即 `type`，`data:` 即 JSON 序列化的 `Envelope`。
- **无状态请求 + seq 续传**：断线重连带 `Last-Event-ID`（= seq），服务器补发缺失事件。这条是联机的地基。

`travel` 目标 `status !== "built"` 时返回 `E_FORBIDDEN`（本表 §7 的“越权”语义在此扩展为“规划/在建点不可进入”，不新增错误码）。

其余返回形状：`travel` 的 `scene` = `MapViewScene` + `{ dialogues: Array<{id, npcId, title, lines:string[]}>; anchorLocId?: string }`（用户场景才带 `anchorLocId`）；`tick` 的 `moved` = `Array<{actorId, name, from, to}>`；`dialogue` 的 `npc` = `{id, name}`、`lines: string[]`。

## 6. LLM 工具名（function calling）

- 格式严格 `<moduleId>.<verb>`，例：`trade.buy`、`study.quiz`、`social.gift`。
- 引擎工具（非模块）用保留命名空间：`core.move`、`core.observe`、`core.wait`、`core.say`、`actor.emote`。
- 每个工具必须有：`description`（≤120 字）、`parameters`（zod → JSON Schema）、`costWeight`。
- 工具返回统一 `{ ok, facts: string[], proposals: Proposal[] }`。
- 注入策略：只注入"当前地点 + 在场者"相关模块的工具，且总数 ≤ 24 个（超了按 manifest `priority` 截断，防止工具表膨胀）。

### 10.7 2.2.0 → 2.3.0：结算语义收口（Issue #1）

> 这一版把「引擎记账」从「能跑」变成「能讲清楚」，**不新增 op 原语**（12 个仍然闭集）。

| 变更 | 类型 | 兼容性 |
|---|---|---|
| `Arbiter.apply` 增加 `opts?: {mode, expectedSeq}` | 只增 | 旧调用兼容（默认 atomic = 文档原语义） |
| `ApplyResult` 增加 `mode`；`ok` 明确为「这批是否提交」 | 语义澄清 | 依赖「部分成功仍 ok」的调用方需显式传 partial |
| 默认提交语义 = **atomic**（任何一条被拒 → 整批不落库） | 修正实现与文档一致 | 见 02 §4 |
| `attr.delta` 增加 `mustKeep?` | 只增 | 支付类模块应显式使用 |
| `Store.flush(roomId)` | 新增 | 内存实现 no-op；`Turn` 在 commit 前 await |
| 新错误码 `E_PRECONDITION` / `E_STORE_FAULT` | 只增 | 28 → 30 |
| 限额改为**整回合累计**（`causedBy` 为回合键），被拒的批不吃额度 | 修正 | 拆批不再能绕过 `maxDeltaPerTurn` / `xWritesPerTurn` |
| 权限只看 `cause.type`（可信来源），`proposal.by` 仅用于报告 | 安全修正 | 伪造 `by` 不再能推进时间/代写记忆 |
| 同房间 `apply` 串行排队 | 实现强化 | 并发提交不再交错读快照 |

### 10.8 2.3.0 → 3.0.0：持久化闭环与整批失败形状（Issue #1 复审）

> 2.3.0 的结算语义是对的，但**生产路径（FileStore + Turn）没闭环**：写盘失败后内存已变、重启后 seq 取错、
> 整批失败用占位提案冒充 rejected。这一版只有引擎内部接口变化，**12 个 op 原语与模块作者看到的 API 不变**。

| 变更 | 类型 | 为什么是 major |
|---|---|---|
| `ApplyResult.error?: {code,message}`（整批失败用，`rejected` 为空） | 新增字段 | `expectedSeq` 失败不再伪造 `attr.set` 占位提案（去掉 `as unknown as Proposal`） |
| `EventLog.load(roomId): Promise<number>` | 新增方法 | `expectedSeq`/回合开头的 seq 必须取自载入后的日志，否则重启后首回合必报 `E_SEQ_GAP` |
| `EventLog.append` 文件实现改为**写盘先行**（原子 tmp→rename），返回 Promise | 语义修正 | 写盘失败 → 内存/seq 不变；`Turn` 收到 `E_STORE_FAULT` 且未 commit，重试安全 |
| 载入遇 seq 断档/重复 → 截断到连续前缀并写回（`FileStore.repaired`） | 实现修正 | 坏档不再让房间永久读不出；代价是丢弃断档之后的尾部事件（会打日志） |
| `Store.flush` 是**必选方法**（不是可选） | 破坏性 | 严格 semver 下新增必选成员 = major：任何第三方 `Store` 实现都会编译失败。这就是 3.0.0 的唯一理由（引擎内部接口，模块作者无感） |

> **兼容性说明**：模块（Module）、导演（Director）、前端看到的契约没有变化：`apiVersion` 仍是 2，
> `PROMPT_VERSION` 不变，12 个 op 原语不变。只有"自己实现 Store/EventLog"的代码需要适配。
